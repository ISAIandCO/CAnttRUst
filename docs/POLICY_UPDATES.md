# Обновление политики и выпуск

Расширение по-прежнему работает офлайн: список CA и ключи CT-логов поставляются внутри подписанной версии. Установки пользователей не скачивают политику при посещении сайтов.

## Ежедневная сверка

`Monitor security policy` запускается в 04:17 UTC и вручную. Проверяются:

- NUC CT-список Яндекса: <https://browser-resources.s3.yandex.net/ctlog/ctlog.json>;
- PEM-набор Госуслуг: <https://gu-st.ru/content/Other/doc/russiantrustedca.pem> (ссылка опубликована в [документации Сбера](https://developers.sber.ru/help/certificates/how-to)).

Для CT значимы ключ, log ID, оператор, статус и его время, границы `temporal_interval`. Дата скачивания, версия исходного JSON, описание, email и URL лога сами по себе не вызывают релиз. URL и MMD не используются текущей офлайн-проверкой; при реализации сетевых inclusion proofs их потребуется включить в сравнение.

Пустой/повреждённый ответ, неизвестный оператор или статус, tiled logs, неверный log ID, неподдерживаемый ключ, откат версии/времени, исчезновение более половины логов и отсутствие пригодного Yandex shard требуют ручного разбора. Сетевые запросы имеют таймаут и предел размера; TLS-проверка не отключается, редиректы не принимаются. Изменение адреса источника проверяется человеком.

Из PEM-набора извлекаются самоподписанные CA с ожидаемым именем. Новые DER-отпечатки **добавляются** к ограничиваемым корням; старые автоматически не удаляются. Для новых корней сохраняются PEM, DER/SPKI SHA-256, сроки действия и источник в `src/policy/ca-evidence/`. Это не установка сертификата в Firefox и не предоставление ему доверия.

Монитор обнаруживает новые корни в указанном наборе. Он не обнаружит автоматически новый CA под другим именем или по новому адресу: такой переход требует изменения источника/проверки после ручного подтверждения. Изменение только промежуточного CA не требует новой версии, если корень остаётся прежним.

## PR и версия

При значимых изменениях бот готовит PR из `bot/security-policy` в `main`, повышая patch-версию в `package.json`, `package-lock.json` и `manifest.firefox.json`. Он проверяет пакет и воспроизводимость до открытия PR; CI дополнительно запускается явно на ветке бота. Дата/метаданные источника не создают ежедневных коммитов для уже ожидающего PR с той же политикой. Если источники вернулись к принятой политике, ненужный PR закрывается при успешной полной сверке.

Автоматического слияния нет. Перед слиянием проверьте новые ключи, изменение доверия и корневые отпечатки. Самоподпись корня и записанный хеш источника подтверждают структуру/целостность данных, но не доказывают происхождение. Изменения должны подтверждаться публикациями оператора/CA.

Источники проверяются независимо: ошибка одного не отменяет результат другого. Ошибки попадают в issue «Не удалось проверить источники политики CAnttRUst» и делают запуск красным; PR явно сообщает о неполной проверке. Ошибка не заменяет принятые данные пустыми. После восстановления источников issue закрывается.

В Settings → Actions → General должна быть включена опция **Allow GitHub Actions to create and approve pull requests**. Бот использует обычный `GITHUB_TOKEN`; отдельный PAT не нужен. Workflows и секреты не изменяются ботом.

## Правила статусов CT

Это явно заданная политика CAnttRUst, а не заявление о полном совпадении со всеми правилами браузеров:

- `usable`: SCT принимается с указанного времени включительно;
- `readonly`, `retired`: могут засчитываться SCT, выданные **до** указанного времени перехода; граница исключается;
- `rejected`: SCT не засчитывается независимо от времени выдачи;
- `pending`, `qualified`, неизвестный/некорректный статус: SCT не засчитывается.

Подпись всё равно проверяется. `temporal_interval` по-прежнему применяется к `notAfter` сертификата, а не к SCT timestamp. Требование Яндекса и усиленный режим с двумя операторами сохранены. Изменение статуса лога покрыто тестом с настоящим сертификатом.

## Публикация в AMO

`Publish to AMO` запускается при изменении `package.json` или `manifest.firefox.json` в `main`, а также вручную **только из main**. Таким образом, принятие PR с новой версией запускает отправку без отдельного ручного workflow. Это относится и к обычным релизам с повышением версии.

Используются уже существующие secrets `AMO_JWT_ISSUER` и `AMO_JWT_SECRET`. Перед отправкой запрашивается точная версия через аутентифицированный AMO API. Уже одобренная или ожидающая проверки версия повторно не отправляется; отключённая версия, ошибка API или конфликт канала требуют разбора. Повторный запуск после сетевого сбоя сначала проверяет, успела ли предыдущая отправка создать версию.

Сборка проходит типизацию, тесты, проверку политики, bundle scan, web-ext lint и проверку воспроизводимости. В AMO передаётся архив исходников из того же коммита. Отправка не означает мгновенную публикацию: Mozilla может отправить версию на проверку.

В 04:47 UTC тот же workflow **только проверяет статус**, ничего не публикуя. Результат для текущей версии main записывается в Job Summary и `status.json`: `not-submitted`, `unreviewed`, `public` или `disabled`. История старых версий доступна в Developer Hub; ежедневная проверка отслеживает только текущую версию main. После успешной команды отправки Summary отдельно сообщает «отправлено», без утверждения о публикации. Отключённая версия делает проверку красной.

`Release signed XPI` запускается тем же изменением версии в `main`, что и AMO workflow, либо вручную из `main`. Каналы работают независимо: ожидание проверки магазина не задерживает GitHub Release. Для одного ID Mozilla не принимает повторный номер версии даже в другом канале, поэтому релиз `0.1.2` даёт AMO-сборку `0.1.2` и self-hosted сборку `0.1.2.1`. Следующий релиз `0.1.3` выше обеих версий. ID остаётся прежним; `update_url` присутствует только в self-hosted сборке. Тег — `v0.1.2`, файл — `canttrust-0.1.2_git.xpi`, а `updates.json` содержит фактическую версию XPI `0.1.2.1`. Суффиксы `_amo`/`_git` допустимы в имени файла, но не в числовом поле `version`.

Если GitHub Release уже существует со всеми файлами, повторный запуск его пропускает. Если Mozilla уже подписала unlisted-версию, но публикация на GitHub оборвалась, workflow скачивает подписанный XPI повторно, сверяет SHA-256 из AMO, ID, версию и `update_url`, затем публикует релиз. Ожидающая проверки или отключённая unlisted-версия повторно не отправляется: после одобрения можно повторить workflow. Исходники передаются Mozilla в обоих каналах. Изменение политики не затрагивает README, зависимости или исходный код автоматически.

## Локальная проверка

```sh
npm ci
npm run package:firefox
npm run check:reproducible
node scripts/update-ct-policy.mjs
node scripts/update-ca-policy.mjs
```

Два последних скрипта скачивают источники и при значимых изменениях изменяют файлы политики локально; они ничего не публикуют. `node scripts/prepare-policy-update.mjs` предназначен для чистого CI checkout: он также повышает версию при изменении политики. `node scripts/bump-version.mjs` повышает patch-версию синхронно в трёх файлах.
